# Project02 - AI翻译助手

> 这是一个适合学习 AI 翻译产品的项目实战案例。当前项目采用 `React + TypeScript + Vite + Express` 实现，支持多语言互译、源语言自动识别、翻译风格切换、备选译文采用、本地翻译历史以及 mock/API 双模式演示。它仍不是一个具备术语库、文档翻译、批量翻译和翻译质量评估能力的企业级翻译平台，但已经从最初的「单段翻译原型」升级为一个体验完整、可直接落地演示的单点翻译工具。

## 一、先理解这个项目在练什么

这个项目最适合训练的是以下三类能力：

1. 如何把一个很常见的 AI 能力做成清晰、直接、可演示的单点工具。
2. 如何围绕“输入文本 -> 选择参数 -> 获取结果”设计一个最小可用产品闭环。
3. 如何理解翻译类 AI 产品从 Demo 到企业级工具之间的能力差距。

如果你是初学者，这个项目能帮助你快速理解一个 AI 工具型产品最小 MVP 的典型结构：

- 输入区
- 参数区
- 结果区

如果你是技术人员，这个项目适合你练习：

- React 表单与状态管理
- 前后端接口串联
- mock 模式与真实模型模式切换
- 文本类工具的前端交互细节

如果你是想转型 AI 产品经理，这个项目很适合用来理解：

- 单点 AI 工具如何定义核心价值
- 体验层设计如何影响产品易用性
- 为什么“能翻译”不等于“翻得适合业务场景”

## 二、项目目标与用户场景

这个项目要模拟的问题可以概括为一句话：

> 用户输入一段文本，指定源语言、目标语言和翻译风格后，系统快速返回一版可阅读的翻译结果。

它适合模拟的典型场景包括：

- 日常中英文内容互译
- 技术文档快速翻译
- 海外资料初步理解
- 不同表达风格的文案转换

这类场景很适合做成 AI 工具原型，因为它天然具备：

- 明确输入
- 明确输出
- 用户即时反馈

但要注意，当前项目更准确的定位是“文本翻译原型”，而不是完整翻译工作台。

## 三、当前项目能力概览

根据真实代码，这个项目当前已经实现了：

- 源语言与目标语言选择
- **源语言自动识别**（`自动检测` 选项，后端基于 Unicode 启发式 + API 模式下的模型识别）
- 一键交换源语言和目标语言
- `正式 / 口语 / 技术` 三种翻译风格
- 文本翻译接口调用
- **备选译文展示与一键采用**
- **复制译文、输入字符计数**
- **本地翻译历史**（localStorage 持久化，支持恢复、删除、清空）
- **独立错误提示**（错误不再污染结果区）
- mock/API 双模式切换

但它当前也有非常明确的边界：

- 不支持文档上传翻译
- 不支持长文分段处理
- 不支持术语库
- 不支持批量翻译与翻译质量评分

因此，这个项目当前的定位是：

> 一个体验完整、可直接演示的「单点文本翻译工具」，而不是企业级翻译平台。

## 五、技术栈与实现方式

### 1. 当前真实可运行部分

- 前端：React 18 + TypeScript + Vite
- 样式：Tailwind CSS
- 后端：Express + TypeScript
- 模型 SDK：OpenAI Node SDK
- 本地开发：前端 `5173`，后端 `3000`

### 2. 当前最值得注意的实现特点

这个项目虽然小，但有几个很适合学习的点：

- 前端支持多语言切换
- 前端支持翻译方向互换
- 前端支持风格参数
- 后端支持 mock 模式降级

这说明它不是一个只会“把文本发给模型”的最粗糙 Demo，而是已经开始考虑工具产品的可用性。

### 3. 当前没有落地的企业级翻译能力

当前项目还没有实现：

- 行业术语库
- 公司品牌语气统一
- 多版本翻译结果比较
- 文档批量翻译
- 人工校对流
- 质量评分与回译校验

所以你在阅读这个项目时，重点不应该是它“功能多不多”，而是它是否把最核心的翻译体验闭环做清楚了。

## 六、运行方式

> 下面所有命令都以**项目根目录**（即 `Project02-AI翻译助手/`）为起点，使用相对路径，clone 到任意位置都能直接运行。

### 方式一：一条命令同时启动前后端（推荐）

项目根目录提供了 `start-dev.sh`，会自动安装依赖、准备 `.env` 并同时拉起前后端：

```bash
cd Project02-AI翻译助手
./start-dev.sh
```

脚本会在前台运行后端与前端，按 `Ctrl + C` 即可同时退出。

### 方式二：手动分步启动

如果你想理解每一步在做什么，可以手动执行。

#### 1. 安装前端依赖

在项目根目录执行：

```bash
pnpm install
```

#### 2. 安装服务端依赖

进入 `server` 目录执行：

```bash
cd server
pnpm install
```

#### 3. 配置环境变量

服务端提供了 `.env.example`，你可以复制为 `.env`：

```bash
cp .env.example .env
```

默认配置如下：

```env
OPENAI_API_KEY=
PORT=3000
```

说明如下：

- 不配置 `OPENAI_API_KEY`：进入 mock 模式，适合演示和学习
- 配置 `OPENAI_API_KEY`：进入 API 模式，调用真实模型进行翻译与语言识别

#### 4. 启动后端（在 `server/` 目录下）

```bash
pnpm dev
```

#### 5. 启动前端（在项目根目录下，另开一个终端）

```bash
pnpm dev
```

### 访问地址与接口

- 前端页面：`http://localhost:5173`
- 后端健康检查：`http://localhost:3000/health`
- 翻译接口：`POST /api/translate`（`sourceLang` 传 `auto` 即自动识别源语言）
- 语言识别接口：`POST /api/detect`

项目在 `vite.config.ts` 中把 `/api` 代理到了 `http://localhost:3000`，因此无需额外配置跨域。

## 七、这个项目最值得看的代码点

建议你按下面顺序阅读。

### 1. `src/components/Translator.tsx`

这是整个项目最关键的前端文件。

它把翻译工具最核心的体验拆得很清楚：

- 输入原文
- 选择源语言
- 选择目标语言
- 选择翻译风格
- 查看结果

同时还有几个很有工具感的细节：

- 一键交换源语言和目标语言
- 备选译文一键采用
- 复制译文、字符计数与独立错误提示

这类细节虽然实现简单，但对工具产品体验很重要。

### 2. `src/hooks/useTranslator.ts`

这是这一版新增、也是最值得看的前端文件。

它把组件里的状态逻辑全部收敛了进来：

- 翻译动作、loading 与错误状态
- 备选译文与识别语言的回写
- 翻译历史的 localStorage 持久化、恢复、删除与清空

把「状态逻辑」与「界面渲染」分离，是 React 工具类应用很常用的工程手法，也方便后续做单元测试。

### 3. `src/services/api.ts`

这个文件负责封装 `translateText()` 与 `detectLanguage()` 请求。

它的价值在于：

- 让组件层不直接写 `fetch`
- 统一错误处理
- 为后续增加鉴权、超时或日志埋点留出空间

### 4. `server/services/translator.ts`

这是当前项目最值得认真看的后端文件，承载了真正的翻译能力：

- 基于 Unicode 区间的轻量语言识别（`detectLanguageHeuristic`），API 模式下优先用模型并以启发式兜底
- 根据 `OPENAI_API_KEY` 切换 mock/API 模式
- 根据 `style` 选择不同翻译风格指令
- 把源语言和目标语言映射成中文语义标签

mock 模式下，它并不是简单返回固定一句话，而是会根据语言和风格生成主译文与备选译文，这一点很适合学习。

`server/routes/translate.ts` 则专注做参数校验与路由分发（含 `/translate` 与 `/detect` 两个接口），与服务逻辑分层清晰。

### 5. `server/index.ts`

这个文件展示了一个最轻量的 AI 工具型后端形态：

- 注册 `/api`
- 提供 `/health`（含当前模式与支持语言）
- 展示当前运行模式

对新手来说，这个结构足够简单，也足够实用。

## 八、从产品和技术角度，应该如何理解这个项目

### 1. 从产品角度看

这个项目已经具备翻译产品原型最重要的三个感觉：

- 参数明确
- 结果即时
- 交互简单

这足以支撑一个很清晰的单点工具演示。

### 2. 从技术角度看

它当前主要完成的是：

- 前端翻译交互
- 风格参数透传
- 后端翻译接口
- mock/API 双模式

而真正决定企业翻译工具价值的底层能力还没有落地，例如：

- 专业术语控制
- 文本上下文一致性
- 长文分片翻译
- 多版本候选排序
- 翻译质量校验

### 3. 从学习角度看

这个项目很适合作为“AI 单点工具产品化”的练习样本：

1. 先把一个能力做成清晰可用的工具。
2. 再增强输入参数和交互体验。
3. 最后再往专业场景和企业需求扩展。

## 九、如果你是产品经理，应该重点观察什么

### 1. 翻译产品真正的差异，不只在模型能力

很多人会以为翻译产品的核心只是“模型翻得准不准”。

实际上真实用户还会关心：

- 风格是否合适
- 术语是否统一
- 结果是否可直接使用
- 是否支持业务上下文

当前项目虽然简单，但已经开始从“风格控制”切入这一层。

### 2. 工具产品很依赖细节体验

像这个项目里的这些点都很重要：

- 语言切换
- 方向互换
- 加载状态
- 结果只读展示

这些细节决定了用户是否愿意频繁使用。

### 3. 企业翻译系统真正难的是一致性和流程

真实企业不会只要求“翻译出来”。

它们通常更关心：

- 品牌表达是否统一
- 技术术语是否统一
- 是否需要人工复核
- 是否能批量处理内容

当前项目适合你用来理解“基础翻译工具”向“专业翻译系统”演化的方向。

## 十、能力现状与下一步改造

### 已实现（v2.0.0）

下面几项在最初版本中只是「改造方向」，当前版本已经落地，可直接作为阅读和模仿的样例：

- ✅ 展示备选译文 + 一键采用（`alternatives`）
- ✅ 源语言自动识别（`auto` + `/api/detect`）
- ✅ 翻译历史（localStorage，支持恢复 / 删除 / 清空）
- ✅ 复制译文、字符计数、独立错误提示

### 下一步改造方向

如果你要把这个项目继续推进、写进作品集，可以从下面方向中至少做一次有价值的改造。

#### 改造方向 1：支持文档翻译

如果想往企业级方向推进，可以继续增加：

- 上传文档
- 长文分段翻译与拼接
- 导出翻译结果

#### 改造方向 2：增加术语库或场景模板

这是把“通用翻译”升级为“业务翻译工具”的关键。

可以考虑增加：

- 技术术语模板
- 商务邮件模板
- 产品文档模板
- 公司品牌语气模板

#### 改造方向 3：翻译质量校验

让结果更可信，可以尝试：

- 回译（back-translation）校验
- 多版本候选打分与排序
- 关键术语一致性检查
