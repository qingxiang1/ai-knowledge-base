# Project06 - AI 代码助手（可直接运行的真实代码引擎 Demo）

> 一个**真正会分析代码**的助手：粘贴代码，它用本地引擎**真实计算**静态指标、**真实逐行检查**常见问题、**真实应用**语言安全的自动修复；描述需求，它从内置片段库返回**经过验证、可直接运行**的实现。
> 技术栈 `React + TypeScript + Vite + Express`。**不配置任何 API Key 也能完整使用**；配置 `OPENAI_API_KEY` 后，大模型会**基于真实静态分析事实**给出更自然的生成/解释/优化/修复结果。

## 一、和「假代码 Demo」的区别

原始版本的问题：mock 模式无论你输入什么，`生成`只是把你的话塞进函数名，`解释/优化/修复`返回的是与你代码**毫不相关**的固定模板。本项目把这层补成真的：

- ✅ **指标是算出来的**：行数构成、注释率、函数数、最大嵌套深度、圈复杂度近似、最长行——全部来自对你**实际粘贴代码**的扫描。
- ✅ **问题是查出来的**：逐行检测 `==`/`!=`、`var`、遗留 `console.*`、`debugger`、空 `catch`、超长行、`TODO`、`eval` 等，**带真实行号与级别**。
- ✅ **修复是真改的**：对 JS/TS 应用 `var→let`、`==→===`、`!=→!==`、去行尾空白等**安全转换**，返回真正修改后的代码。
- ✅ **语言安全**：自动修复按语言门控——例如 **Python 的 `==` 不会被误改**（Python 用 `==` 判等，没有 `===`）。
- ✅ **片段是真实的**：`生成`走内置片段库（防抖、节流、深拷贝、快排、二分、去重、邮箱校验……），都是可直接运行的正确实现，未命中则如实告知。
- ✅ **离线可用 + 优雅降级**：无需 API Key、零第三方库；API 模式失败时自动回退本地真实结果。

## 二、四种动作分别真实做了什么

| 动作 | 本地真实能力 | 输出 |
| --- | --- | --- |
| **生成** generate | 片段库意图匹配 | 命中片段的可运行代码 + 片段名 |
| **解释** explain | 静态分析（analyzer.ts） | 语言探测 + 行数/注释率/函数数/嵌套/复杂度/最长行 |
| **优化** optimize | 静态分析 + 规则检查 | 基于真实指标的优化建议 + 带行号的问题清单 |
| **修复** fix | 规则检查 + 安全自动修复（linter.ts） | 修复后代码 + 已应用修复列表 + 问题清单 |

## 四、运行方式

```bash
# 1. 安装依赖（根目录 + server）
pnpm install
cd server && pnpm install && cd ..

# 2.（可选）配置环境变量
cd server && cp .env.example .env && cd ..
#   留空 OPENAI_API_KEY = 本地真实引擎；填写后 = 模型基于真实分析叙述

# 3. 启动（两个终端）
cd server && pnpm dev      # 后端，默认 http://localhost:3000
pnpm dev                   # 前端，默认 http://localhost:5173
```

- 前端页面：`http://localhost:5173`
- 健康检查：`http://localhost:3000/health`

> 环境变量：`OPENAI_API_KEY`、`OPENAI_MODEL`（默认 `gpt-4o-mini`）、`OPENAI_BASE_URL`（可接 DeepSeek 等兼容服务）、`PORT`。

## 五、API 接口

`POST /api/code`，请求体 `{ "prompt": "<代码或需求>", "language": "JavaScript", "action": "generate|explain|optimize|fix" }`。

`curl` 验证 fix（启动后端后）：

```bash
curl -X POST http://localhost:3000/api/code \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"var a=1\nif(a==null){}","language":"JavaScript","action":"fix"}'
# 返回修复后代码（var→let、==→===）与已应用修复列表——真实转换
```

## 六、两种模式的工作原理

```
代码/需求 ──► 本地引擎（analyzer / linter / snippets）真实处理
                        │
        ┌───────────────┴────────────────┐
    mock 模式                          api 模式
  直接返回真实结果              把「真实静态分析事实」喂给模型，
  （指标/问题/修复/片段）        让它据此生成更自然的解释与建议
                                （不编造事实，失败则降级为本地结果）
```

关键点：**分析与修复永远是本地真实执行的**，API Key 只决定「文字叙述」是模板还是模型润色。这与 Project05 的设计一脉相承——用真实事实约束模型，避免幻觉。

## 七、动手练习

1. **加一条 Lint 规则**：在 `linter.ts` 增加「函数参数过多（> 5）」检测。
2. **加一个安全修复**：把单引号统一为双引号（注意跳过字符串内容）。
3. **扩充片段库**：在 `snippets.ts` 增加「LRU 缓存」「Promise 并发限制」等真实片段。
4. **多语言度量**：完善 `analyzer.ts` 对 Python 缩进块的函数与嵌套识别。
5. **接入真实 AST**：用 `@babel/parser` / `typescript` 编译器 API 替换正则，获得更准的复杂度与结构分析。

## 八、如果你是产品经理，重点观察什么

1. **「能跑」与「能改对」的差距**：生成代码容易，但真正难的是**安全地修改已有代码**——本项目的语言门控（Python 不改 `==`）就是一个最小但关键的正确性约束。
2. **正则 vs AST 的工程权衡**：当前用正则做轻量分析，零依赖、够用但有边界；升级到 AST 更准但更重。这是代码工具的典型取舍。
3. **可解释性**：每条建议都对应真实指标或真实行号，便于开发者信任与采纳。
4. **能力边界**：这是单文件、规则驱动的助手，不是接入仓库上下文、能跨文件重构的 IDE 级工具——但它把「分析—检查—修复」内核做实了。
