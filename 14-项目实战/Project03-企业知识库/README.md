# Project03 - 企业知识库

> 这是一个适合学习 AI 知识库（RAG）产品的项目实战案例。它采用 `React + TypeScript + Vite + Express` 前后端分离，支持文档上传、文档切片、**真实检索增强问答（带来源引用）**、按文档限定检索范围、本地持久化以及 mock/API 双模式演示。检索环节采用**混合检索**（embedding 向量语义召回 + 词法精确匹配，融合排序）：API 模式用 OpenAI embeddings，离线 mock 模式用本地特征哈希 embedding，因此无需任何外部向量库即可直接落地跑通整条 RAG 链路——既能理解 RAG 的「向量召回 + 检索—生成」闭环，又能平滑演化到接入持久化向量库与重排序的企业级系统。

## 一、先理解这个项目在练什么

这个项目最适合练的是三件事：

1. 你如何把“上传资料 + 提问问答”做成一个最小可演示的 AI 产品原型。
2. 你如何把前端页面、后端接口、文件上传和模型调用串成一个完整闭环。
3. 你如何识别一个“看起来像知识库”的 Demo，距离真正的企业级 RAG 系统还有哪些关键差距。

如果你是初学者，这个项目可以帮助你建立 AI 知识库产品的基本认知。

如果你是技术人员，这个项目适合你用来练习：

- React 前端交互组织
- Express 接口拆分
- 文件上传流程
- mock 模式与真实 API 模式切换
- 从 Demo 继续演化到真实 RAG 系统的改造路径

如果你是想转型 AI 产品经理，这个项目最值得观察的地方不是“它有多复杂”，而是：

- 知识库产品最小 MVP 应该先做到什么
- 什么功能只是演示层
- 什么能力才是真正决定企业可用性的底层能力

## 二、项目目标与用户场景

这个项目要解决的问题可以概括为一句话：

> 让用户上传企业资料后，可以围绕资料发起问答，快速得到一个看起来像“企业知识助手”的产品原型。

它适合模拟的典型场景包括：

- 新员工查找制度、流程和操作规范
- 客服团队查询产品知识、售后说明和常见问题
- 销售团队查询方案资料、报价说明和行业案例
- 内部团队围绕项目文档、需求文档、培训资料进行问答

但要注意，当前项目更偏向“知识库产品原型”，而不是“已经打通真实文档检索链路的生产系统”。

## 三、当前项目能力概览

结合真实代码看，这个项目当前已经具备以下能力：

- 前端展示聊天区、文档列表和上传弹窗
- 支持上传 `txt`、`md` 纯文本文件，并**真实读取正文、按段落切片入库**
- 文档列表展示真实切片数、文件大小，支持删除
- **支持勾选文档以限定提问的检索范围（`doc_ids` 真实生效）**
- **真实检索增强问答**：根据问题在切片中检索 top-k 相关片段，答案与「参考来源」均来自真实检索结果
- 来源展示真实片段正文、所属文档标题与相关度，并**高亮命中的检索词**（可解释检索）
- 文档、切片与**对话历史均本地持久化**（JSON 文件），服务重启后保留
- 内置两份示例文档与示例问题，首次启动即可直接提问演示
- 支持 `OPENAI_API_KEY` 存在与否两种运行模式：mock 模式由检索片段直接合成答案，API 模式把检索片段作为上下文喂给模型生成接地答案

当前的能力边界（也是后续改造方向）：

- 离线 mock 模式用的是**本地特征哈希 embedding**（非学习得到的语义向量），语义泛化弱于真实模型；配置 `OPENAI_API_KEY` 后即切换为 OpenAI 语义 embedding
- 仅解析纯文本（txt/md），暂不解析 pdf/docx 等二进制文档
- 暂无长文重排序（rerank）、权限隔离、多租户与回答质量评估

它的价值在于：**整条「上传 → 切片 → 向量化 → 检索 → 引用 → 生成」的 RAG 链路是真实跑通的**，你既能直接看到向量召回与检索—生成闭环如何工作，也能清楚看到它与接入持久化向量库 + 重排序的企业级系统之间还差哪些环节。

## 五、技术栈与实现方式

当前项目的技术栈可以拆成两层来理解。

### 1. 当前真正已经跑起来的实现

- 前端：React 18 + TypeScript + Vite
- 样式：Tailwind CSS
- 后端：Express + TypeScript
- 文件上传：Multer
- 接口通信：基于浏览器 `fetch` 的简单封装
- 本地开发：前端 `5173`，后端 `8000`

### 2. 检索实现方式：embedding 向量 + 混合检索

这一版的检索环节是**真正的向量检索**：对切片和查询分别做 embedding，按**余弦相似度**召回，并与词法匹配融合排序（见下文「混合检索」）。向量化有两种后端，由是否配置 `OPENAI_API_KEY` 自动切换：

- **API 模式**：调用 OpenAI `text-embedding-3-small` 生成语义向量，具备语义泛化能力（近义词、换一种问法也能召回）。
- **离线 mock 模式**：使用**本地特征哈希 embedding**（对中文二元组 / 英文词做 FNV 哈希到 2048 维稠密向量并 L2 归一化）。无需任何外部服务或 API Key，`clone` 下来即可直接跑通真实的「向量化 → 余弦相似度 → top-k」检索。

检索采用**混合检索（Hybrid Search）**：向量语义召回 + 词法精确匹配，融合排序。

实现要点（见 `server/services/embeddings.ts` 与 `retriever.ts`）：

- **召回**：候选门槛为「向量余弦相似度达标」**或**「词法覆盖率过半」——语义相近或精确命中关键词的切片都能进入候选，兼顾召回。
- **排序**：融合分 = `0.65 × 语义相似度 + 0.35 × 词法覆盖率`，语义为主、精确匹配为辅。前端会展示每条来源的「语义 / 词法」子分，让混合检索过程可见。
- **阈值**：向量相似度按本地 / API 两档设阈，无关问题如实返回空结果，不强行给弱相关片段。
- **缓存**：切片向量按 `切片 id + 模型标识` 内存缓存，切换 mock/API 自动重算；API 模式批量向量化减少调用。
- 命中词用于来源**高亮**（可解释性）。

> 这是一条可直接落地的混合检索实现：离线即可演示「向量召回 + 词法精排」，配置 API Key 后立即获得语义级 embedding。下一步可把内存向量换成持久化向量库（Chroma / pgvector）并加入重排序（rerank）。

## 六、运行方式

> 下面所有命令都以**项目根目录**（即 `Project03-企业知识库/`）为起点，使用相对路径，clone 到任意位置都能直接运行。

### 方式一：一条命令同时启动前后端（推荐）

```bash
cd Project03-企业知识库
./start-dev.sh
```

脚本会自动安装依赖、准备 `.env` 并同时拉起前后端，按 `Ctrl + C` 即可同时退出。

### 方式二：手动分步启动

#### 1. 安装前端依赖

```bash
pnpm install
```

#### 2. 安装服务端依赖

```bash
cd server
pnpm install
```

#### 3. 配置环境变量

```bash
cp .env.example .env
```

默认配置很简单：

```env
OPENAI_API_KEY=
PORT=8000
```

说明如下：

- 不配置 `OPENAI_API_KEY`：进入 mock 模式，答案由检索到的文档切片直接合成
- 配置 `OPENAI_API_KEY`：进入 API 模式，检索到的切片作为上下文喂给模型，生成接地（grounded）答案

#### 4. 启动后端（在 `server/` 目录下）

```bash
pnpm dev
```

#### 5. 启动前端（在项目根目录下，另开一个终端）

```bash
pnpm dev
```

### 访问地址与接口

- 前端页面：`http://localhost:5173`
- 后端健康检查：`http://localhost:8000/health`
- 文档接口：`POST /api/v1/documents/upload`、`GET /api/v1/documents`、`DELETE /api/v1/documents/:id`
- 问答接口：`POST /api/v1/chat/ask`（`doc_ids` 可限定检索范围）

项目在 `vite.config.ts` 中配置了代理，前端访问 `/api` 会自动转发到 `http://localhost:8000`，无需额外配置跨域。

## 七、这个项目最值得看的代码点

建议你按下面顺序阅读。

### 1. `src/App.tsx`

这里决定了整个页面骨架：

- 左侧主区域是 `ChatInterface`
- 右侧侧栏是 `DocumentList`
- 顶部按钮打开 `UploadModal`
- 文档加载、选择与删除统一交给 `useKnowledgeBase` Hook，选中的文档范围会传给问答组件

你可以把它理解为一个非常典型的 AI 工具页布局：

- 顶部是全局动作
- 中间是核心交互
- 右侧是上下文资产

### 2. `src/components/ChatInterface.tsx`

这个组件体现了知识库问答前端最基本的交互闭环：

- 用户输入问题
- 本地先插入用户消息
- 调用 `askQuestion()`
- 返回后插入助手消息
- 渲染参考来源
- 异常时显示错误提示

这部分很适合新手理解“AI 聊天页面最小可用交互”应该如何组织。

### 3. `src/components/DocumentList.tsx`

这里体现的是知识库产品的第二条主线：文档资产管理。

它实现了：

- 展示文档标题、类型、大小与真实切片数
- 勾选文档以限定提问检索范围
- 删除文档

文档资产管理是知识问答的前提——知识问答不是孤立能力，它一定依赖「资料资产管理 + 检索范围控制」。

### 4. `src/components/UploadModal.tsx`

上传弹窗展示了知识库最重要的输入入口：

- 选择文件
- 输入标题
- 输入描述
- 调用上传接口

这部分虽然简单，但它决定了未来是否能扩展为：

- 批量上传
- 文件夹上传
- URL 导入
- 飞书/Notion/Confluence 同步

### 5. `server/services/`（最值得看的部分）

后端把 RAG 链路拆成了几个独立、可替换的服务，建议重点阅读：

- `chunker.ts`：把文档正文按空行分段、并对长段落按句末标点二次切分。
- `embeddings.ts`：向量化。API 模式调用 OpenAI embeddings；离线 mock 模式用本地特征哈希 embedding。**想接入真实向量库，主要改这一个文件。**
- `retriever.ts`：混合检索——向量余弦相似度负责语义召回，词法覆盖率负责精确匹配，按融合分排序取 top-k；切片向量按模型标识在内存缓存。返回语义/词法子分并标注命中词供高亮。
- `rag.ts`：先检索再生成——mock 模式由检索片段合成答案，API 模式把片段作为上下文喂给模型生成接地答案。
- `document-store.ts`：文档与切片的本地 JSON 持久化，首次启动写入种子文档。

`server/routes/documents.ts` 现在会真实读取上传文件正文、调用 `chunker` 切片、入库；`chunk_count` 是真实切片数量，不再是随机值。

### 6. `server/routes/chat.ts`

这是问答链路的入口，它把请求交给 `rag.answerQuestion()`：

- mock 模式：答案由真实检索到的切片直接合成，`sources` 即检索命中片段
- API 模式：检索到的切片作为上下文，模型据此生成接地答案
- `doc_ids` 会真实驱动检索范围，`top_k` 真实控制返回片段数量
- 「参考来源」来自真实检索结果，带文档标题、片段正文与相关度

> 这正是 RAG 的核心：先「检索」出与问题相关的知识片段，再让模型「基于这些片段」作答，从而让回答可溯源、可控制范围。本项目用 embedding 向量检索（离线可用本地 embedding），让你在不依赖外部向量库的情况下完整看清这条链路。

### 7. `src/services/api.ts`

这个文件负责统一封装前端 API 请求。

它的价值在于：

- 让组件层不用直接写 `fetch`
- 把上传、列表、删除、提问等动作集中管理
- 为后续接入鉴权、重试、错误码映射留下空间

## 八、从产品和技术角度，应该如何理解这个项目

这个项目非常适合作为一个“知识库产品演化样本”来学习。

### 1. 从产品角度看

它已经具备知识库产品的三个基础面：

- 资料进入系统
- 用户围绕资料发起问题
- 系统返回答案和来源

这意味着它已经具备了演示型 MVP 的基本形态。

### 2. 从技术角度看

它当前主要完成的是：

- 页面搭建
- 接口串联
- 文件上传
- 模型调用
- mock 降级

而真正决定企业知识库质量的关键能力，还没有落地完整版本，例如：

- 文档解析质量
- 分块策略
- 向量检索效果
- 重排序策略
- 权限隔离
- 数据持久化
- 知识更新机制

### 3. 从学习角度看

这个项目最大的价值不是“直接上线”，而是让你建立一条非常清晰的认知链路：

1. 先做一个能演示的知识库原型。
2. 再识别哪些地方只是前台展示。
3. 最后继续往真实 RAG、企业级治理和多数据源接入演化。

## 九、如果你是产品经理，应该重点观察什么

如果你想从这个项目里学习 AI 产品设计，建议重点观察下面几个问题。

### 1. 上传文档不等于知识库完成

很多初学者会把“文件能上传”误当成“知识库已经建好”。

实际上中间还隔着很多关键环节：

- 文档解析是否成功
- 文档如何切块
- 分块粒度是否合理
- 向量是否生成
- 检索是否准确
- 回答是否带引用
- 引用是否可追溯

### 2. 问答页面不等于真实 RAG

当前项目的聊天界面已经很像一个知识助手，但这并不意味着它已经实现真实的知识增强问答。

这会帮助你形成一个很重要的判断：

> AI 产品中“体验层可演示”与“底层能力可交付”往往不是同一阶段完成的。

### 3. 知识库产品真正难的是数据治理

一个真正可落地的企业知识库，难点通常不在聊天框，而在：

- 文档来源杂乱
- 数据持续更新
- 同名知识冲突
- 权限隔离复杂
- 回答可信度难评估

这个项目现在正好适合作为“前台原型已搭好，后台治理还没展开”的学习样本。

## 十、能力现状与下一步改造

### 已实现（v2.0.0）

下面几项在最初版本中是「待补齐」或「演示型」，当前版本已经真实落地：

- ✅ 上传文档真实解析正文、切片入库（`chunk_count` 为真实切片数）
- ✅ 按 `doc_ids` 限定检索范围的勾选问答体验
- ✅ 真实检索增强问答：来源来自真实命中片段，带文档标题与相关度
- ✅ 文档、切片与对话历史本地持久化，重启后保留；内置种子文档开箱即用
- ✅ **混合检索**：embedding 向量语义召回 + 词法精确匹配融合排序（API 模式用 OpenAI embeddings，离线 mock 模式用本地哈希 embedding）
- ✅ 来源片段展示「语义/词法」子分并高亮命中检索词（可解释性）

### 下一步改造方向

#### 改造方向 1：接入持久化向量库与混合检索

向量检索已经跑通，下一步可把它产品化、规模化：

- 把内存向量缓存换成持久化向量库（Chroma / pgvector / Qdrant），切片向量随文档入库
- 在向量召回基础上加入词法检索做**混合检索（Hybrid Search）**，兼顾语义与精确匹配
- 引入重排序（rerank）进一步提升 top-k 质量

#### 改造方向 2：支持更多文档类型与处理状态

- 解析 pdf / docx 等二进制文档
- 文档状态流转 `pending -> processing -> completed/failed` 与失败重试
- 大文件异步处理与进度展示

#### 改造方向 3：补齐持久化与多数据源

- 文档元数据迁移到 PostgreSQL、原始文件存对象存储（当前为本地 JSON 持久化）
- 飞书 / Notion / Confluence 等数据源同步

#### 改造方向 4：补齐企业级能力

- 用户登录与权限控制、多租户隔离
- 回答引用跳转到原文位置
- 审计日志、命中率与问答效果分析

## 十一、怎么把这个项目讲成作品集

如果你面试时要介绍这个项目，不要只说“我做了一个企业知识库”，而要讲清楚产品边界和你的认知深度。

你可以这样表达：

> 我做了一个企业知识库（RAG）应用，打通了「上传 → 切片 → 向量化 → 检索 → 引用 → 生成」的完整链路：上传文档会被真实解析切片入库，提问时对查询与切片做 embedding，按余弦相似度检索 top-k，答案基于命中片段生成并附带可溯源、可高亮的来源引用，还支持按文档限定检索范围与本地持久化。我用「API 模式 OpenAI embeddings + 离线本地哈希 embedding」的双后端设计，让向量检索在无任何外部向量库依赖下也能直接演示，并把向量化与检索单独封装，便于平滑接入持久化向量库 + 混合检索 + 重排序。我在这个项目里重点理解了 RAG 的向量召回与检索—生成机制，以及它与企业级系统在向量库、权限治理、引用溯源上的差距。

这样的表达会比“我做了一个 AI 聊天页面”更有说服力。

## 十二、最小复盘模板
