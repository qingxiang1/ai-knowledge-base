# Project07 - AI 客服系统（可直接运行的真实客服引擎 Demo）

> 一个**真正会查、会答、会转人工**的客服系统：本地引擎**真实分类意图**（置信度可解释、非随机）、从 **FAQ 知识库检索**答案、按订单号**真实查表**返回物流状态、并按规则**判定是否转人工**。
> 技术栈 `React + TypeScript + Vite + Express`。**不配置任何 API Key 也能完整使用**；配置 `OPENAI_API_KEY` 后，大模型会**基于检索到的知识库事实**生成更自然的回复（RAG 式，不编造价格/政策/订单）。

## 一、和「假客服 Demo」的区别

原始版本的问题：意图置信度是 `Math.random()`（假的）；回复是每个意图一段**固定模板**，并不真正回答你的问题；说「请提供订单号」却**没有任何订单数据**；Socket.IO 在真实模式下直接回「请通过 API 接口获取回复」。本项目把这些补成真的：

- ✅ **意图是算出来的**：按关键词命中计分选意图，置信度由「命中数 + 与次优意图的差距」**确定性推导**，并返回命中的关键词，完全可解释。
- ✅ **答案从知识库来**：内置 12 条 FAQ，用中英文混合分词检索最相关条目并给出**相似度分数**——这是 RAG 的最小内核。
- ✅ **订单真的查得到**：内置模拟订单库，从消息中识别订单号（如 `DD20260601`）后**真实查表**返回商品/状态/物流/预计送达。
- ✅ **转人工有真实规则**：投诉、明确要求人工、或「意图不明 + 知识库未命中且置信度低」时自动建议转人工，并给出原因。
- ✅ **离线可用 + 优雅降级**：无需 API Key、零额外依赖；API 模式失败时自动回退本地标准答复。

## 二、一条消息的真实处理流程

```
用户消息
   │
   ├─ 意图识别（intent.ts）           → 意图 + 真实置信度 + 命中关键词
   ├─ 显式转人工？                    → 直接给转接话术
   ├─ 订单意图/含订单号？(orders.ts)  → 真实查表，返回订单状态
   ├─ FAQ 检索（knowledge.ts）        → 命中则用知识库答案（带相似度）
   └─ 否则意图模板兜底
   │
   └─ 转人工判定（reply.ts）+ 快捷回复建议
```

mock 模式直接返回上面这条确定性结果；API 模式把「检索到的事实」喂给大模型润色（不编造）。

## 四、运行方式

```bash
# 1. 安装依赖（根目录 + server）
pnpm install
cd server && pnpm install && cd ..

# 2.（可选）配置环境变量
cd server && cp .env.example .env && cd ..
#   留空 OPENAI_API_KEY = 本地真实引擎；填写后 = 模型基于知识库事实润色

# 3. 启动（两个终端）
cd server && pnpm dev      # 后端，默认 http://localhost:3000
pnpm dev                   # 前端，默认 http://localhost:5173
```

- 前端页面：`http://localhost:5173`
- 健康检查：`http://localhost:3000/health`

> 环境变量：`OPENAI_API_KEY`、`OPENAI_MODEL`（默认 `gpt-4o-mini`）、`OPENAI_BASE_URL`（可接 DeepSeek 等兼容服务）、`PORT`。

## 五、API 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/chat` | 处理消息，返回回复 + 意图/置信度/来源/订单/转人工/快捷建议 |
| `GET` | `/api/meta` | 当前模式、FAQ 列表、演示订单号 |
| `GET` | `/api/chat/:sessionId/history` | 会话历史 |
| `GET` | `/health` | 健康检查 |

`curl` 验证订单查询（启动后端后）：

```bash
curl -X POST http://localhost:3000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"content":"帮我查下订单 DD20260601 到哪了","session_id":"demo"}'
# 返回真实订单状态/物流，source=order，intent=order_query
```

演示可用订单号：`DD20260601`（已发货）、`DD20260612`（待发货）、`DD20260618`（已签收）。

## 六、动手练习

1. **扩充知识库**：在 `knowledge.ts` 增加 FAQ，观察检索是否命中；尝试调整相似度阈值 `0.18`。
2. **改进检索**：把关键词重叠打分换成 TF-IDF 或向量检索（接 Embedding），对比召回质量。
3. **加一个工具**：仿照 `orders.ts` 增加「物流轨迹查询」或「优惠券核销」工具。
4. **完善转人工**：增加「同一会话连续 3 次未命中即转人工」的规则。
5. **接入工单**：转人工时生成一条工单（含意图、摘要、会话历史）写入内存/数据库。

## 七、如果你是产品经理，重点观察什么

1. **置信度必须可信**：把随机置信度换成「可解释的计分」是这次最重要的修正——客服系统里，置信度直接决定是否转人工，假置信度会误导路由。
2. **答案要可溯源**：每条回复都标注来源（FAQ 命中 / 订单查询 / 标准话术 / 模型），并给相似度分数，这是企业客服敢上线的前提。
3. **AI 的边界与兜底**：识别不了就转人工，是好客服产品的底线设计，而不是失败。
4. **RAG 的最小形态**：FAQ 检索 + 模型润色，就是「先检索后生成」，能在保证不乱编的前提下让回复更自然。

## 八、继续进阶的方向

- 向量检索替代关键词（Embedding + 相似度），提升 FAQ 召回
- 真实工单系统与人工坐席后台
- 多轮澄清（追问槽位，如退款需先确认订单）
- 满意度评价与会话质检
- 接入真实订单/物流/CRM 系统

## 九、怎么把它写进作品集 / 讲给面试官

> 我做了一个可直接运行的 AI 客服系统：实现了可解释的意图分类（置信度由关键词命中计分推导，而非随机）、FAQ 知识库检索（RAG 最小内核，带相似度分数）、按订单号真实查表的订单工具，以及基于规则的转人工判定。它有本地真实引擎与「模型基于知识库事实润色」两种模式、可优雅降级，前端展示意图/来源/转人工/快捷回复等可溯源信息。这个项目让我理解了客服系统的关键不在「能聊」，而在**可信的置信度、可溯源的答案与合理的兜底**。

## 十、最小复盘模板

1. 为什么「随机置信度」在客服系统里是危险的？它会影响哪个下游决策？
2. FAQ 检索 + 模型润色，相比「直接让模型回答」，好在哪？
3. 什么情况下应该主动转人工？把它写成可执行的规则。
4. 订单查询为什么要做成「工具查表」而不是让模型回答？
5. 要把这个 Demo 推向企业客服平台，第一个要补的能力是什么？
