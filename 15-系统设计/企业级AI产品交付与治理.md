# 2026 企业级 AI 产品交付与治理

> 更新基线：2026-08-12。本章只把“已经影响企业方案的变化”纳入主线；厂商模型名称、价格和榜单应在具体选型时重新查证，不作为长期架构依据。

## 一、2026 技术雷达：该学什么、学到什么程度

| 主题 | 状态 | 产品判断 | 企业落地点 |
| --- | --- | --- | --- |
| 推理/多模态模型 | 采用 | 模型能力更强不等于任务 ROI 更高 | 用企业样本按质量、延迟、成本、合规做路由 |
| Structured Output / Tool Calling | 采用 | 是可靠集成的基础，不等于完整 Agent | Schema 校验、输出处理、幂等、超时、重试 |
| RAG 2.0 | 采用 | 重点从“接向量库”转向数据质量、权限与评测 | Hybrid Search、Rerank、引用、ACL、增量索引 |
| Agentic Workflow | 采用但设边界 | 优先确定性工作流；仅在路径不可预先枚举时增加自治 | 状态持久化、预算、审批、补偿、人工接管 |
| MCP | 采用 | 解决 Agent/应用与工具、资源的标准连接 | 服务注册、授权、信任分级、版本与审计 |
| A2A | 试点 | 解决独立 Agent 间发现、委派和结果交换，不替代 MCP | 先证明跨团队/跨厂商协作价值，再建设 |
| 长期记忆 | 受控试点 | 记忆是数据产品，不是无限聊天记录 | 用户可见可删、来源/TTL、权限、污染防护 |
| 合成数据与模型辅助评测 | 采用但人工校准 | 可扩充覆盖面，不能替代真实样本与专家判断 | 切片、人工锚点、评审一致性、漂移监控 |
| 小模型/端侧/私有化 | 场景采用 | 隐私、延迟、稳定吞吐可能比前沿能力重要 | 分层路由、量化验证、硬件容量、运维能力 |
| 自主多 Agent 组织 | 观察 | 协调成本和故障面常高于演示价值 | 限定任务、隔离权限、可终止、全链路追踪 |

### 已过时或危险的学习方式

- 用单一公开榜单决定企业模型选型。
- 把 Prompt 调优当作评测、数据和流程设计的替代品。
- 默认所有问题都应做 Agent，且让 Agent 直接持有高权限账号。
- RAG 只测“回答看起来不错”，不测检索、引用、权限和无答案。
- 把 MCP Server 的工具描述当成可信输入，忽略服务来源和用户确认。
- 上线后只看调用量，不看任务成功、业务结果、风险事件和单位成本。

## 二、协议边界：API、MCP 与 A2A

```text
用户/业务系统
     ↓
AI 应用或 Agent Host
     ├── 普通 API：稳定、明确的系统到系统调用
     ├── MCP：Agent ↔ 工具/资源/Prompt
     └── A2A：独立 Agent ↔ 独立 Agent
```

| 问题 | 首选 |
| --- | --- |
| 已知后端服务的确定性事务调用 | 普通 API/事件 |
| 让不同 AI Host 以统一方式发现与调用工具 | MCP |
| 跨团队或跨厂商的独立 Agent 发现、委派、返回产物 | A2A |
| 单应用内部的几个固定步骤 | 工作流/代码，不必引入 A2A |

截至 2026-08-12，MCP 最新规范页面为 `2026-07-28`，除核心 Resources、Prompts、Tools 外，已列出长任务、Skills over MCP 和 MCP Apps 等可选扩展。企业采用时必须做能力协商、版本兼容和明确授权，不应假设所有客户端支持同一扩展。

## 三、从立项到退役的八道门

| 门禁 | 必答问题 | 必要产物 | 通过标准 |
| --- | --- | --- | --- |
| G0 机会 | 问题是否真实，规则/流程优化能否解决？ | 机会一页纸、现状基线 | 业务 Owner、受益人、基线明确 |
| G1 可行性 | 数据、模型、集成与政策是否允许？ | Spike、数据清单、风险初筛 | 用真实样本完成最小验证 |
| G2 立项 | 价值是否覆盖建设、运行与变更成本？ | PRD、TCO/ROI、RACI | 有预算、Owner、停止条件 |
| G3 设计 | 正常、异常、高风险路径是否可控？ | 架构、威胁模型、评测计划 | 产品/架构/安全/法务会签 |
| G4 发布 | 效果、性能、安全、运维是否达标？ | 发布清单、模型卡、回滚方案 | 回归门禁通过，值班责任明确 |
| G5 灰度 | 真实用户是否得到净价值？ | 灰度报告、事件与反馈队列 | 指标无显著倒退，风险可控 |
| G6 运营 | 质量、成本、漂移是否持续可控？ | 周/月报、Bad Case、风险台账 | SLO、预算和整改闭环达标 |
| G7 退役 | 数据、权限、依赖如何安全退出？ | 迁移、归档、删除、通知方案 | 凭证撤销、数据处置、审计完成 |

## 四、企业 AI PRD 必须多出的内容

传统功能描述之外，至少增加：

1. **能力边界**：能做、不能做、需要拒绝或转人工的任务。
2. **数据契约**：来源、分类、权限、用途、留存、删除和输出去向。
3. **模型策略**：候选模型、路由、版本、回退、区域与供应商退出。
4. **评测设计**：黄金集、切片、指标、阈值、Owner 和回归频率。
5. **风险控制**：注入、泄漏、错误动作、偏见、误导、未授权使用。
6. **人工控制**：何时确认、何时复核、何时接管、如何申诉和撤销。
7. **非功能需求**：SLO、容量、延迟、可用性、RTO/RPO、可观测性。
8. **成本模型**：单任务成本、预算上限、异常消费阻断和成本分摊。
9. **运营闭环**：反馈、Bad Case、知识更新、版本发布和事故响应。

## 五、评测体系：从 Demo 分数到业务证据

### 5.1 四层指标

| 层级 | 典型指标 | 常见误区 |
| --- | --- | --- |
| 组件 | 检索 Recall@K、工具参数准确率、结构化输出通过率 | 组件好不代表任务成功 |
| 任务 | 端到端成功率、忠实性、完成时长、人工接管率 | 只测平均值，不测风险切片 |
| 产品 | 采用率、重复使用、建议采纳、满意度 | 把调用量当价值 |
| 业务 | AHT、解决率、收入、返工、损失/风险避免 | 没有上线前基线和对照 |

### 5.2 黄金集最低结构

```yaml
case_id: unique-id
scenario: 业务场景
risk_tier: low|medium|high
input: 用户输入与必要上下文
expected_behavior: 期望行为，而非只写唯一答案
forbidden_behavior: 不得发生的行为
expected_sources: 可接受来源
tool_expectation: 工具/参数/是否需要确认
slices: [语言, 用户角色, 数据权限, 长尾类型]
reviewer: 领域专家
last_verified_at: 2026-08-12
```

### 5.3 发布回归门禁示例

- 高风险切片禁行行为发生率必须为 0。
- 权限泄漏测试必须为 0；越权工具调用必须为 0。
- 关键任务成功率不低于当前生产版本，或业务 Owner 明确签署例外。
- P95 延迟、单任务成本和失败率不超过预算。
- 模型裁判指标必须用人工锚点校准，并跟踪一致性。

## 六、Agent 的企业控制面

### 6.1 工具风险分级

| 级别 | 示例 | 默认策略 |
| --- | --- | --- |
| R0 只读公开 | 查公开文档、天气 | 可自动，保留调用日志 |
| R1 只读内部 | 查客户、财务、代码 | 按用户身份鉴权，输出防泄漏 |
| R2 可逆写入 | 建草稿、创建未发布工单 | 显示预览，可撤销，限制范围 |
| R3 高影响写入 | 发消息、付款、删数据、改权限 | 明确确认/双人审批、强审计、限额 |
| R4 禁止自治 | 人事处分、重大信贷/医疗/法律最终决定 | 仅辅助，不允许 Agent 做最终决定 |

### 6.2 必备控制

- Agent 使用短期、任务级凭证，不共享个人长期 Token。
- 授权同时校验“用户能否做”和“Agent 在此任务中是否应做”。
- 工具参数在服务端重新校验，绝不直接信任模型输出。
- 所有写入有幂等键；可逆操作设计补偿；不可逆操作前确认。
- 设置步骤、时间、Token、金额和调用次数预算，支持一键终止。
- 记录请求、策略判断、工具、结果、确认人和版本，对敏感数据最小化。

## 七、安全与合规基线

### 7.1 OWASP GenAI 重点映射

2025 版风险包括 Prompt Injection、敏感信息披露、供应链、数据/模型投毒、不当输出处理、过度代理、系统 Prompt 泄漏、向量/Embedding 弱点、错误信息和无界消耗。产品方案不能只写“内容审核”，应把风险映射到具体控制和测试用例。

| 风险 | 产品/系统控制 |
| --- | --- |
| Prompt Injection | 隔离不可信内容、工具权限不由文本决定、注入测试集 |
| 敏感信息披露 | 输入/输出 DLP、最小检索范围、脱敏、日志最小化 |
| 供应链/投毒 | 模型与依赖清单、来源签名、索引写入审批、回滚 |
| 不当输出处理 | Schema/类型/安全校验，进入 SQL/HTML/Shell 前转义 |
| 过度代理 | 工具分级、限额、确认、沙箱、职责分离 |
| 无界消耗 | 预算、速率限制、循环检测、队列和熔断 |

### 7.2 NIST 与欧盟 AI 法案

- NIST AI RMF 使用 `Govern / Map / Measure / Manage` 组织风险工作；2024 年发布生成式 AI Profile。2026 年 NIST 已启动 AI RMF 1.0 修订，并发布关键基础设施可信 AI Profile 概念说明。企业模板应保留版本字段，避免把框架当一次性检查表。
- 欧盟 AI 法案采用风险分级。根据欧盟委员会 2026-08-03 更新页面：禁止性条款的大部分要求已于 2025-02 生效，GPAI 规则于 2025-08 生效，透明度规则于 2026-08 生效；高风险要求的页面当前说明从 2027-12-02 起适用。涉及欧盟市场时须由法务结合角色、用途和最新修订确认，教程不构成法律意见。

## 八、可观测性与 FinOps

每次 AI 任务至少应关联：`trace_id、user/agent identity、tenant、use_case、prompt/policy version、model、retrieval/tool trace、latency、tokens/cost、outcome、feedback、risk event`。

| 看板 | 核心问题 |
| --- | --- |
| 业务价值 | 哪些用户和任务真正得到结果？ |
| 质量 | 哪类样本退化，何时开始，影响多大？ |
| 可靠性 | 哪个模型、工具、数据源造成失败或延迟？ |
| 安全治理 | 谁访问了什么、策略如何决定、是否发生越权？ |
| 成本 | 成本由哪个业务/租户/步骤产生，是否值得？ |

成本优化顺序：先消除无价值调用，再缩短上下文和结果，再做缓存/批处理/路由，最后才讨论单价。降成本不能破坏关键切片质量和合规要求。

## 九、大型企业 RACI

| 事项 | A（最终负责） | R（执行） | C（会签/咨询） |
| --- | --- | --- | --- |
| 业务目标与流程 | 业务 Owner | 产品经理 | 运营、财务、用户代表 |
| 模型/系统方案 | 技术 Owner | 算法、工程、架构 | 产品、安全、采购 |
| 数据用途与权限 | 数据 Owner | 数据/平台团队 | 安全、隐私、法务 |
| 评测与上线门禁 | 产品 Owner | 产品、算法、测试 | 业务专家、风险团队 |
| 高风险接受 | 风险/业务高管 | 产品与控制团队 | 法务、合规、安全 |
| 运行与事件响应 | 服务 Owner | SRE/运维与研发 | 供应商、产品、业务 |

## 十、供应商选型评分卡

| 维度 | 建议权重 | 必查项 |
| --- | ---: | --- |
| 企业任务效果 | 25% | 真实黄金集、长尾和风险切片 |
| 安全与合规 | 20% | 数据使用、驻留、加密、审计、认证、事件通知 |
| 可靠性与运维 | 15% | SLA、限额、容量、区域、版本弃用政策 |
| 集成与可迁移 | 15% | API/协议、导出、模型切换、退出协助 |
| TCO | 15% | 推理、存储、网络、工程、评测、运营和承诺消费 |
| 厂商与生态 | 10% | 财务/路线稳定性、支持、合作伙伴、锁定风险 |

必须用同一企业样本和同一约束做 PoC；合同中明确数据是否用于训练、子处理方、审计权、版本变更通知、退出和数据删除证明。

## 十一、季度技术更新机制

1. **每月**：核对模型/API 弃用、价格、区域和配额；只更新易变数据表。
2. **每季度**：用固定黄金集重跑候选模型；评估 MCP/A2A/框架是否真正降低集成成本。
3. **每半年**：重做威胁模型、红队和供应商风险审查。
4. **每年**：重算用例组合 ROI、平台复用率和退出计划，关闭低价值项目。

每条趋势记录：`观察日期、权威来源、成熟度、适用场景、风险、验证实验、Owner、复审日期`。不要因厂商发布会直接改生产路线图。
