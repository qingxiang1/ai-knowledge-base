# 12 第十二章：从 demo 到生产的检查清单

学习时长：75 分钟

本章类型：上线前检查 + 风险控制

本章产物：一份可用于复盘和上线评审的生产检查清单

## 12.0 本章要完成什么

前面章节已经覆盖了大模型项目的主要工程链路：

```text
数据清洗
tokenizer
预训练
SFT
LoRA / QLoRA
蒸馏
评测
推理调试
vLLM 部署
```

但 demo 和生产之间还有很长距离。

demo 只需要证明：

```text
这条链路能跑通。
```

生产系统需要证明：

```text
这条链路可复现、可评测、可监控、可回滚、可负责。
```

本章会把上线前需要检查的事项系统整理出来。

你会逐步检查：

- 数据来源是否可追溯
- 数据清洗是否可复现
- 训练配置是否可复现
- 模型版本是否明确
- 评测集是否覆盖关键业务
- 是否有人工作业和复核流程
- 推理日志是否足够排障
- 服务是否有超时、重试、限流
- 是否处理敏感信息
- 是否有监控、告警和回滚方案

完成本章后，你应该能回答：

```text
为什么部署不是上线结束？
如果模型今天变差了，怎么定位原因？
如果新版本出问题，怎么回滚？
```

## 12.1 demo 和生产的核心差距

demo 常见目标：

```text
能训练
能推理
能生成报告
能展示几个好例子
```

生产系统目标：

```text
稳定服务真实用户
对错误有监控
对版本有记录
对数据有追踪
对风险有兜底
对事故能回滚
```

所以从 demo 到生产，不是只多一个部署命令。

它需要一整套工程纪律。

## 12.2 数据检查

上线前先检查数据。

### 12.2.1 数据来源是否可追溯

你需要知道：

```text
数据来自 FAQ、工单、客服对话、人工标注还是蒸馏？
每批数据是什么时间产生的？
谁审核过？
是否包含敏感信息？
```

本课程中，原始数据在：

```text
data/raw/customer_support_raw.jsonl
```

清洗配置在：

```text
configs/prepare_sft_data.json
```

清洗摘要在：

```text
outputs/data_prep/prepare_sft_summary.json
```

生产项目里，这些都应该进入版本记录。

### 12.2.2 rejected 样本是否检查过

不要只看 accepted 数据。

还要看：

```text
outputs/data_prep/customer_support_rejected.jsonl
```

重点确认：

- 是否误删了重要业务问题
- 是否低质量样本被正确过滤
- 是否重复样本过多
- 是否过滤规则太严

数据清洗不是越狠越好。

清洗规则应该服务业务目标。

### 12.2.3 是否处理敏感信息

客服数据可能包含：

- 手机号
- 地址
- 订单号
- 身份信息
- 支付信息
- 用户隐私描述

生产训练前必须有脱敏策略。

本课程样例数据没有覆盖完整隐私治理，但真实项目不能跳过。

## 12.3 训练检查

### 12.3.1 训练配置是否可复现

每次训练至少要记录：

```text
模型名
数据文件
配置文件
代码版本
依赖版本
随机种子
输出目录
训练日志
```

本课程把训练参数放在：

```text
configs/
```

例如：

```text
configs/sft_minimal_cpu_local.json
configs/sft_qlora_16gb.json
configs/distill_train.json
```

生产中不要只记一句：

```text
我们用 Qwen 微调了一版。
```

这无法复现。

### 12.3.2 模型版本是否明确

模型版本至少包含：

```text
base model
adapter path
merged model path
训练数据版本
训练配置版本
发布日期
负责人
```

例如：

```text
base_model: Qwen/Qwen2.5-0.5B-Instruct
adapter_path: outputs/sft_qwen25_16gb
merged_model: outputs/qwen25_cs_merged
```

如果线上模型回答出问题，你必须能定位它来自哪次训练。

### 12.3.3 是否保存 tokenizer

模型目录必须能自包含加载。

至少要有：

```text
config.json
model.safetensors 或 adapter_model.safetensors
tokenizer.json
tokenizer_config.json
special_tokens_map.json
```

缺 tokenizer 会给推理和部署带来很多隐性问题。

## 12.4 评测检查

### 12.4.1 是否有业务评测集

上线前必须有业务评测集。

本课程示例：

```text
data/eval/customer_eval_sample.jsonl
```

真实评测集应该覆盖：

- 高频问题
- 长尾问题
- 边界问题
- 业务规则容易变的问题
- 安全和合规问题
- 用户表达不清的问题

### 12.4.2 是否生成评测报告

至少运行：

```bash
make report-eval
```

或样例路线：

```bash
make report-eval-sample
```

报告输出：

```text
outputs/eval/customer_report.md
```

生产上线评审中，不应该只展示成功样例。

必须展示失败样例和改进计划。

### 12.4.3 是否分析过背题风险

运行：

```bash
make retrieve-similar
make analyze-preds
```

关注：

```text
评测问题是否和训练问题高度相似？
模型回答是否复述训练答案？
换一种问法是否仍然正确？
```

如果模型只会回答训练集中几乎一样的问题，它还不能算泛化稳定。

## 12.5 服务检查

### 12.5.1 服务是否有超时

模型服务必须设置超时。

没有超时会导致：

- 请求堆积
- 上游服务卡死
- 用户长时间等待
- 故障扩散

### 12.5.2 是否有限流

没有限流时，突发流量可能打爆 GPU 服务。

限流维度可以包括：

- 用户
- 应用
- IP
- API key
- 模型版本

### 12.5.3 是否有重试策略

重试要谨慎。

可以对短暂网络错误重试。

但不要对所有错误无脑重试。

否则会放大故障。

### 12.5.4 是否记录推理日志

至少记录：

```text
请求时间
模型版本
输入长度
输出长度
延迟
错误码
调用方
```

敏感输入输出要脱敏或按合规要求处理。

不要随意把用户原文长期明文保存。

## 12.6 安全检查

### 12.6.1 敏感信息

检查模型是否会：

- 泄露训练数据中的隐私
- 输出用户敏感信息
- 要求用户提供不必要信息
- 记录或回显敏感字段

### 12.6.2 越权建议

客服助手不能随意承诺：

```text
一定退款
一定赔偿
一定修改订单
绕过平台规则
```

回答应遵守业务流程。

### 12.6.3 幻觉和编造

如果模型不知道，应引导查询或转人工。

不要编造政策、时效或赔偿规则。

## 12.7 监控和告警

生产环境至少监控：

```text
QPS
错误率
平均延迟
P95 / P99 延迟
GPU 显存
GPU 利用率
超时率
输出长度异常
人工投诉率
```

评测指标也可以定期回归：

```text
keyword coverage
人工通过率
高风险样本失败率
```

一旦新版本指标明显下降，要能报警。

## 12.8 回滚方案

上线前必须知道怎么回滚。

至少准备：

```text
上一版模型目录
上一版配置
上一版服务启动方式
回滚负责人
回滚触发条件
```

触发条件可以是：

- 错误率上升
- 延迟超阈值
- 投诉增加
- 关键评测集失败
- 安全样本失败

没有回滚方案，不建议上线。

## 12.11 常见误区

### 12.11.1 没有评测就上线

只看几个成功 demo 不够。

必须有覆盖关键业务的评测集。

### 12.11.2 没有日志就排障

没有日志时，线上问题只能靠猜。

至少要知道：

```text
哪个版本
什么输入
什么输出
耗时多少
是否报错
```

### 12.11.3 没有限流就开放服务

模型服务资源昂贵。

没有限流会让少量异常流量影响所有用户。

### 12.11.4 没有回滚

大模型输出存在不确定性。

新版本上线必须能快速退回旧版本。
