# Project03 - 企业知识库

> 这是一个适合学习 AI 知识库（RAG）产品的项目实战案例。它采用 `React + TypeScript + Vite + Express` 前后端分离，支持文档上传、文档切片、**真实检索增强问答（带来源引用）**、按文档限定检索范围、本地持久化以及 mock/API 双模式演示。它使用「轻量词法检索」而非向量检索，因此无需向量数据库即可直接落地跑通整条 RAG 链路——这也让它非常适合用来理解 RAG 的检索—生成闭环，再进一步往向量检索的企业级系统演化。

## 一、先理解这个项目在练什么

这个项目最适合练的是三件事：

1. 你如何把“上传资料 + 提问问答”做成一个最小可演示的 AI 产品原型。
2. 你如何把前端页面、后端接口、文件上传和模型调用串成一个完整闭环。
3. 你如何识别一个“看起来像知识库”的 Demo，距离真正的企业级 RAG 系统还有哪些关键差距。

如果你是初学者，这个项目可以帮助你建立 AI 知识库产品的基本认知。

如果你是技术人员，这个项目适合你用来练习：

- React 前端交互组织
- Express 接口拆分
- 文件上传流程
- mock 模式与真实 API 模式切换
- 从 Demo 继续演化到真实 RAG 系统的改造路径

如果你是想转型 AI 产品经理，这个项目最值得观察的地方不是“它有多复杂”，而是：

- 知识库产品最小 MVP 应该先做到什么
- 什么功能只是演示层
- 什么能力才是真正决定企业可用性的底层能力

## 二、项目目标与用户场景

这个项目要解决的问题可以概括为一句话：

> 让用户上传企业资料后，可以围绕资料发起问答，快速得到一个看起来像“企业知识助手”的产品原型。

它适合模拟的典型场景包括：

- 新员工查找制度、流程和操作规范
- 客服团队查询产品知识、售后说明和常见问题
- 销售团队查询方案资料、报价说明和行业案例
- 内部团队围绕项目文档、需求文档、培训资料进行问答

但要注意，当前项目更偏向“知识库产品原型”，而不是“已经打通真实文档检索链路的生产系统”。

## 三、当前项目能力概览

结合真实代码看，这个项目当前已经具备以下能力：

- 前端展示聊天区、文档列表和上传弹窗
- 支持上传 `txt`、`md` 纯文本文件，并**真实读取正文、按段落切片入库**
- 文档列表展示真实切片数、文件大小，支持删除
- **支持勾选文档以限定提问的检索范围（`doc_ids` 真实生效）**
- **真实检索增强问答**：根据问题在切片中检索 top-k 相关片段，答案与「参考来源」均来自真实检索结果
- 来源展示真实片段正文、所属文档标题与相关度
- 文档与切片**本地持久化**（JSON 文件），服务重启后保留
- 内置两份示例文档，首次启动即可直接提问演示
- 支持 `OPENAI_API_KEY` 存在与否两种运行模式：mock 模式由检索片段直接合成答案，API 模式把检索片段作为上下文喂给模型生成接地答案

当前的能力边界（也是后续改造方向）：

- 使用**词法检索**（中文二元组 + 英文分词的覆盖率打分），而非 embedding 向量检索，语义泛化能力有限
- 仅解析纯文本（txt/md），暂不解析 pdf/docx 等二进制文档
- 暂无长文重排序（rerank）、权限隔离、多租户与回答质量评估
- 对话历史保存在服务端内存中，重启不保留（文档与切片已持久化）

它的价值在于：**整条「上传 → 切片 → 检索 → 引用 → 生成」的 RAG 链路是真实跑通的**，你既能直接看到 RAG 闭环如何工作，也能清楚看到它与向量检索企业级系统之间还差哪些环节。

## 五、技术栈与实现方式

当前项目的技术栈可以拆成两层来理解。

### 1. 当前真正已经跑起来的实现

- 前端：React 18 + TypeScript + Vite
- 样式：Tailwind CSS
- 后端：Express + TypeScript
- 文件上传：Multer
- 接口通信：基于浏览器 `fetch` 的简单封装
- 本地开发：前端 `5173`，后端 `8000`

### 2. 检索实现方式

这一版采用**轻量词法检索**作为 RAG 的检索环节，刻意不引入向量数据库，原因是：

- 无需启动 Chroma 等外部服务，`clone` 下来即可直接跑通整条链路
- 检索逻辑透明、可读，适合先理解「检索—生成」闭环
- 后续可在 `server/services/retriever.ts` 单点替换为 embedding 向量检索

检索打分逻辑（见 `retriever.ts`）：中文按二元组、英文按单词切词，以「查询词命中覆盖率为主、词频密度为辅」对每个切片打分，取 top-k 作为来源。

## 六、运行方式

> 下面所有命令都以**项目根目录**（即 `Project03-企业知识库/`）为起点，使用相对路径，clone 到任意位置都能直接运行。

### 方式一：一条命令同时启动前后端（推荐）

```bash
cd Project03-企业知识库
./start-dev.sh
```

脚本会自动安装依赖、准备 `.env` 并同时拉起前后端，按 `Ctrl + C` 即可同时退出。

### 方式二：手动分步启动

#### 1. 安装前端依赖

```bash
pnpm install
```

#### 2. 安装服务端依赖

```bash
cd server
pnpm install
```

#### 3. 配置环境变量

```bash
cp .env.example .env
```

默认配置很简单：

```env
OPENAI_API_KEY=
PORT=8000
```

说明如下：

- 不配置 `OPENAI_API_KEY`：进入 mock 模式，答案由检索到的文档切片直接合成
- 配置 `OPENAI_API_KEY`：进入 API 模式，检索到的切片作为上下文喂给模型，生成接地（grounded）答案

#### 4. 启动后端（在 `server/` 目录下）

```bash
pnpm dev
```

#### 5. 启动前端（在项目根目录下，另开一个终端）

```bash
pnpm dev
```

### 访问地址与接口

- 前端页面：`http://localhost:5173`
- 后端健康检查：`http://localhost:8000/health`
- 文档接口：`POST /api/v1/documents/upload`、`GET /api/v1/documents`、`DELETE /api/v1/documents/:id`
- 问答接口：`POST /api/v1/chat/ask`（`doc_ids` 可限定检索范围）

项目在 `vite.config.ts` 中配置了代理，前端访问 `/api` 会自动转发到 `http://localhost:8000`，无需额外配置跨域。

## 七、这个项目最值得看的代码点

建议你按下面顺序阅读。

### 1. `src/App.tsx`

这里决定了整个页面骨架：

- 左侧主区域是 `ChatInterface`
- 右侧侧栏是 `DocumentList`
- 顶部按钮打开 `UploadModal`
- 文档加载、选择与删除统一交给 `useKnowledgeBase` Hook，选中的文档范围会传给问答组件

你可以把它理解为一个非常典型的 AI 工具页布局：

- 顶部是全局动作
- 中间是核心交互
- 右侧是上下文资产

### 2. `src/components/ChatInterface.tsx`

这个组件体现了知识库问答前端最基本的交互闭环：

- 用户输入问题
- 本地先插入用户消息
- 调用 `askQuestion()`
- 返回后插入助手消息
- 渲染参考来源
- 异常时显示错误提示

这部分很适合新手理解“AI 聊天页面最小可用交互”应该如何组织。

### 3. `src/components/DocumentList.tsx`

这里体现的是知识库产品的第二条主线：文档资产管理。

它实现了：

- 展示文档标题、类型、大小与真实切片数
- 勾选文档以限定提问检索范围
- 删除文档

文档资产管理是知识问答的前提——知识问答不是孤立能力，它一定依赖「资料资产管理 + 检索范围控制」。

### 4. `src/components/UploadModal.tsx`

上传弹窗展示了知识库最重要的输入入口：

- 选择文件
- 输入标题
- 输入描述
- 调用上传接口

这部分虽然简单，但它决定了未来是否能扩展为：

- 批量上传
- 文件夹上传
- URL 导入
- 飞书/Notion/Confluence 同步

### 5. `server/services/`（最值得看的部分）

后端把 RAG 链路拆成了几个独立、可替换的服务，建议重点阅读：

- `chunker.ts`：把文档正文按空行分段、并对长段落按句末标点二次切分。
- `retriever.ts`：词法检索打分（中文二元组 + 英文分词，覆盖率为主、词频为辅），返回 top-k 来源。**想升级为向量检索，只需替换这一个文件。**
- `rag.ts`：先检索再生成——mock 模式由检索片段合成答案，API 模式把片段作为上下文喂给模型生成接地答案。
- `document-store.ts`：文档与切片的本地 JSON 持久化，首次启动写入种子文档。

`server/routes/documents.ts` 现在会真实读取上传文件正文、调用 `chunker` 切片、入库；`chunk_count` 是真实切片数量，不再是随机值。

### 6. `server/routes/chat.ts`

这是问答链路的入口，它把请求交给 `rag.answerQuestion()`：

- mock 模式：答案由真实检索到的切片直接合成，`sources` 即检索命中片段
- API 模式：检索到的切片作为上下文，模型据此生成接地答案
- `doc_ids` 会真实驱动检索范围，`top_k` 真实控制返回片段数量
- 「参考来源」来自真实检索结果，带文档标题、片段正文与相关度

> 这正是 RAG 的核心：先「检索」出与问题相关的知识片段，再让模型「基于这些片段」作答，从而让回答可溯源、可控制范围。本项目用词法检索替代向量检索，让你在不依赖向量库的情况下完整看清这条链路。

### 7. `src/services/api.ts`

这个文件负责统一封装前端 API 请求。

它的价值在于：

- 让组件层不用直接写 `fetch`
- 把上传、列表、删除、提问等动作集中管理
- 为后续接入鉴权、重试、错误码映射留下空间

## 八、从产品和技术角度，应该如何理解这个项目

这个项目非常适合作为一个“知识库产品演化样本”来学习。

### 1. 从产品角度看

它已经具备知识库产品的三个基础面：

- 资料进入系统
- 用户围绕资料发起问题
- 系统返回答案和来源

这意味着它已经具备了演示型 MVP 的基本形态。

### 2. 从技术角度看

它当前主要完成的是：

- 页面搭建
- 接口串联
- 文件上传
- 模型调用
- mock 降级

而真正决定企业知识库质量的关键能力，还没有落地完整版本，例如：

- 文档解析质量
- 分块策略
- 向量检索效果
- 重排序策略
- 权限隔离
- 数据持久化
- 知识更新机制

### 3. 从学习角度看

这个项目最大的价值不是“直接上线”，而是让你建立一条非常清晰的认知链路：

1. 先做一个能演示的知识库原型。
2. 再识别哪些地方只是前台展示。
3. 最后继续往真实 RAG、企业级治理和多数据源接入演化。

## 九、如果你是产品经理，应该重点观察什么

如果你想从这个项目里学习 AI 产品设计，建议重点观察下面几个问题。

### 1. 上传文档不等于知识库完成

很多初学者会把“文件能上传”误当成“知识库已经建好”。

实际上中间还隔着很多关键环节：

- 文档解析是否成功
- 文档如何切块
- 分块粒度是否合理
- 向量是否生成
- 检索是否准确
- 回答是否带引用
- 引用是否可追溯

### 2. 问答页面不等于真实 RAG

当前项目的聊天界面已经很像一个知识助手，但这并不意味着它已经实现真实的知识增强问答。

这会帮助你形成一个很重要的判断：

> AI 产品中“体验层可演示”与“底层能力可交付”往往不是同一阶段完成的。

### 3. 知识库产品真正难的是数据治理

一个真正可落地的企业知识库，难点通常不在聊天框，而在：

- 文档来源杂乱
- 数据持续更新
- 同名知识冲突
- 权限隔离复杂
- 回答可信度难评估

这个项目现在正好适合作为“前台原型已搭好，后台治理还没展开”的学习样本。

## 十、能力现状与下一步改造

### 已实现（v2.0.0）

下面几项在最初版本中是「待补齐」或「演示型」，当前版本已经真实落地：

- ✅ 上传文档真实解析正文、切片入库（`chunk_count` 为真实切片数）
- ✅ 按 `doc_ids` 限定检索范围的勾选问答体验
- ✅ 真实检索增强问答：来源来自真实命中片段，带文档标题与相关度
- ✅ 文档与切片本地持久化，重启后保留；内置种子文档开箱即用

### 下一步改造方向

#### 改造方向 1：把词法检索升级为向量检索

这是优先级最高、也最能体现 RAG 深度的改造。只需替换 `server/services/retriever.ts`：

- 为每个切片生成 embedding 并入库（Chroma / pgvector / 内存向量均可）
- 查询时做向量相似度检索（可保留词法检索做混合检索 Hybrid Search）
- 引入重排序（rerank）进一步提升 top-k 质量

#### 改造方向 2：支持更多文档类型与处理状态

- 解析 pdf / docx 等二进制文档
- 文档状态流转 `pending -> processing -> completed/failed` 与失败重试
- 大文件异步处理与进度展示

#### 改造方向 3：补齐持久化与多数据源

- 文档元数据迁移到 PostgreSQL、原始文件存对象存储
- 对话历史持久化（当前仍在内存）
- 飞书 / Notion / Confluence 等数据源同步

#### 改造方向 4：补齐企业级能力

- 用户登录与权限控制、多租户隔离
- 回答引用跳转到原文位置
- 审计日志、命中率与问答效果分析

## 十一、怎么把这个项目讲成作品集

如果你面试时要介绍这个项目，不要只说“我做了一个企业知识库”，而要讲清楚产品边界和你的认知深度。

你可以这样表达：

> 我做了一个企业知识库（RAG）应用，打通了「上传 → 切片 → 检索 → 引用 → 生成」的完整链路：上传文档会被真实解析切片入库，提问时按覆盖率对切片打分检索 top-k，答案基于命中片段生成并附带可溯源的来源引用，还支持按文档限定检索范围与本地持久化。我刻意用词法检索替代向量检索，以最低依赖跑通 RAG 闭环，并把检索环节单独封装，便于后续升级为向量检索 + 重排序。我在这个项目里重点理解了 RAG 的检索—生成机制，以及它与企业级系统在向量召回、权限治理、引用溯源上的差距。

这样的表达会比“我做了一个 AI 聊天页面”更有说服力。

## 十二、最小复盘模板

你做完这个项目后，至少应该回答下面几个问题：

1. 这个项目的 RAG 链路由哪几个环节组成？分别对应哪个文件？
2. 为什么“文档上传成功”不等于“知识库已经可用”？
3. 词法检索和向量检索各有什么优劣？什么场景下词法检索就够用？
4. 如果你只能做一次升级，你会优先把哪一段链路换成向量检索还是先做 rerank？
5. 如果把它用在企业场景，最先会遇到什么数据治理与权限问题？

如果你能把这几个问题回答清楚，这个项目就不只是“跑通过”，而是真正进入你的产品与技术理解里了。

## 十三、这个项目适合作为什么阶段的练习

这个项目非常适合作为以下阶段的训练样本：

- 刚开始学 AI 应用开发，想先做一个能演示的知识库原型
- 已经了解聊天产品，想进一步理解知识库产品结构
- 想从 Demo 过渡到 RAG 系统，但还不清楚差距在哪里
- 想向 AI 产品经理转型，需要一个能同时看产品结构与技术边界的案例

如果你前一个项目已经做过 AI 写作助手，那么这个项目正好帮助你从“单轮内容生成”走向“文档资产 + 检索问答”的下一阶段。
